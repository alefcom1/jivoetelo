# Общая инфраструктура с techperevod

> Июль 2026. Что мы переиспользуем у соседнего проекта `alefcom1/techperevod`,
> чего переиспользовать нельзя и почему, и как это экономит память VPS.
> Разобрано по исходникам репозитория, не по памяти.

## 1. Как устроен techperevod (то, что нам важно)

| | techperevod.com | proxy.techperevod.com | Живое Тело |
|---|---|---|---|
| Что это | Сайт-визитка + кабинет, Next.js 14 | Прокси-воркер к AI-провайдерам | Веб-SaaS + Mini App, Next.js 16 |
| Где | VPS под FASTPANEL | VPS в Hetzner (Германия) | VPS reg.ru (Россия) |
| Как запущен | PM2, процесс `techperevod` | Docker-контейнер в чужой сети | Docker Compose |
| База | SQLite файлом на диске (Prisma) | нет, он без состояния | PostgreSQL 17 |
| Деплой | `git reset --hard` + `npm run build` + `pm2 restart --update-env` | `docker compose up -d --build` | `docker compose up -d --build` + `deploy/migrate.sh` |

Воркер — крошечный: один Node-процесс, единственная зависимость `undici`,
роутинг по первому сегменту пути. `/api/v1/*` → Anthropic, `/api/openai/*` →
OpenAI, `/api/deepl/*` → DeepL, `/api/yandex/*` → Yandex Translate. Сайт
знает только общий `PROXY_SECRET`, настоящие ключи живут на воркере.

### Какие данные нужны для подключения

Всё, что нужно нам, — две переменные (уже описано в
[ai-proxy.md](./ai-proxy.md)):

```
ANTHROPIC_BASE_URL=https://proxy.techperevod.com/api
ANTHROPIC_AUTH_TOKEN=<PROXY_SECRET воркера>
```

`ANTHROPIC_API_KEY` при этом не нужен. `PROXY_SECRET` лежит в `.env.local`
воркера на сервере Hetzner — в git его нет.

## 2. Чужие грабли, на которые нам не надо наступать

Всё это уже пройдено на techperevod и задокументировано в их репозитории:

1. **Vercel недоступен с российского VPS.** Сайт в РФ не мог достучаться до
   `techperevod.vercel.app` на уровне TCP, хотя сам воркер до Anthropic
   доходил нормально. Поэтому воркер переехал на собственный сервер.
   *Для нас:* никакого Vercel в цепочке, только `proxy.techperevod.com`.
2. **ECONNRESET на keep-alive.** Пул соединений `undici` держит сокет,
   который удалённая сторона уже закрыла. Лечится `pipelining: 0,
   keepAliveTimeout: 1`. *У нас это учтено с первого дня* в
   `lib/ai/client.ts` — ровно та же настройка.
3. **Порты 80/443 заняты чужим reverse-proxy.** На сервере воркера уже жил
   Caddy другого проекта. Решение: контейнер в той же Docker-сети, наружу
   порт не публикуется, Caddy ходит по имени `techperevod-worker:8787`.
   *Для нас:* приём на будущее, если придётся ставить что-то рядом.
4. **Чужой Caddyfile ведётся руками и может быть переписан.** Их деплой
   затирал site-блок воркера. Решение — идемпотентный
   `ensure-caddy-route.sh`: если блок на месте, ничего не делает; если
   пропал — дописывает и перезагружает Caddy на лету. Хороший приём, если
   мы когда-нибудь поселимся на общий сервер.
5. **`git reset --hard` затирает правки на сервере.** Отсюда железное
   правило: секреты только в `.env.local` (в `.gitignore`), закоммиченный
   `.env` перезаписывается каждым деплоем. *У нас то же самое*: `.env` в
   `.gitignore`, в репозитории только `.env.example`.
6. **`pm2 restart` без `--update-env` держит старое окружение в памяти.**
   Нас не касается — мы на Docker Compose, `up -d` пересоздаёт контейнер с
   новыми переменными.

## 3. Что переиспользуем

### 3.1. Прокси-воркер — да, это основная экономия

Свой воркер нам не нужен: `proxy.techperevod.com` уже развёрнут, работает и
знает дорогу до Anthropic. Экономия — целый контейнер и ~50 МБ памяти на
нашем VPS, плюс отсутствие второго сервера в Германии.

**Но есть нюанс, который стоит закрыть до запуска.** Воркер авторизует
клиента одним `PROXY_SECRET` и ходит к Anthropic одним `ANTHROPIC_API_KEY`.
Это значит:

- утечка секрета у одного проекта требует ротации у обоих;
- счёт от Anthropic будет общий, без разделения по проектам.

Свой расход мы всё равно считаем сами (таблица `ai_usage`), так что
экономику посчитаем точно. Но разделить лимиты и счета чище. Минимальная
правка воркера — сопоставить секрет ключу, не ломая текущего поведения:

```js
// deploy/techperevod-worker/api/index.js, в resolveProvider (набросок)
// Второй проект приносит свой секрет и ходит на свой ключ Anthropic;
// без новых переменных всё работает по-старому.
const secret = readSecret(req);
const key = secret === process.env.PROXY_SECRET_JIVOETELO
  ? process.env.ANTHROPIC_API_KEY_JIVOETELO
  : process.env.ANTHROPIC_API_KEY;
```

Решение за вами: можно стартовать на общем секрете и разделить позже —
код «Живого Тела» менять не придётся, только значение
`ANTHROPIC_AUTH_TOKEN` в `.env`.

### 3.2. SMTP — да, и это закрывает наш долг по напоминаниям

В techperevod уже настроена отправка почты через `nodemailer` с
переменными `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`. Значит,
почтовый ящик и пароль приложения уже есть и проверены в бою.

У нас e-mail-напоминания (хвост M4) стояли заблокированными «нужна
SMTP-инфраструктура». Инфраструктура есть — нужен только тот же ящик или
соседний адрес на том же домене. Отдельный почтовый сервер поднимать не
надо (и не стоило бы в любом случае: своя рассылка с VPS почти гарантированно
уедет в спам).

Важно: письма о питании — чувствительнее, чем заявки на перевод. В теме и
теле письма не должно быть ни веса, ни калорий, только «ваш недельный обзор
готов» со ссылкой.

### 3.3. Методика SEO — да, как шаблон

В `docs/seo-program.md` и `docs/seo-clusters-plan.md` у techperevod описана
рабочая методика: тематические кластеры, формула title через
дифференциатор, борьба с каннибализацией запросов, фазы работ, чек-лист
приёмки работы агента. Это прямо ложится на наш будущий контент-раздел
(«сколько калорий в [блюдо]: честный диапазон» — классический кластер с
риском каннибализации сотен похожих страниц). Переносим методику, не
контент.

### 3.4. Идея админки — да, как приём

У них `/admin` за одним `ADMIN_PASSWORD` вместо полноценной панели. Нам в
плане админка отложена «до реальной нагрузки на модерацию» — когда
понадобится, повторим этот дешёвый приём.

## 4. Что переиспользовать НЕЛЬЗЯ

**Сервер в Hetzner под наши данные — нет.** Это главное ограничение, и оно
не техническое, а юридическое: 152-ФЗ требует, чтобы база с персональными
данными россиян находилась в РФ. Наша база, фотографии еды и всё остальное
состояние обязаны жить на VPS в России.

Отсюда правило: **через Германию может проходить только транзит** —
обезличенное фото или описание блюда по пути к AI, ровно как описано в
согласии пользователя. Ничего, что хранится, туда переносить нельзя. Это
относится и к соблазну «а давайте и базу туда, там сервер мощнее».

**База данных techperevod — не наш случай.** У них SQLite файлом, у нас
PostgreSQL. Общего инстанса, который можно было бы поделить, просто не
существует. Если когда-нибудь оба проекта окажутся на одном российском
сервере, делить Postgres будет можно (разные базы и роли в одном
инстансе) — но сейчас делить нечего.

**Caddy — только при совместном размещении.** Пока проекты на разных
серверах, общего reverse-proxy быть не может.

## 5. Память на нашем VPS: где она уходит и что с этим делать

Ориентировочный расклад для типового VPS 2 ГБ (проверить на месте через
`docker stats` и `free -m`):

| Компонент | Порядок RSS | Комментарий |
|---|---|---|
| PostgreSQL 17 | 150–250 МБ | С настройками по умолчанию берёт больше, чем нужно нашей нагрузке |
| Приложение (Next.js standalone) | 120–200 МБ | Растёт при обработке фото |
| Caddy | 30–50 МБ | |
| Docker daemon + ОС | 200–250 МБ | |
| **Пик при `npm run build`** | **1–1,5 ГБ** | Главный риск OOM на маленьком VPS |

Что сделано в этой волне работ:

1. **Настройки PostgreSQL под маленький сервер** — в `docker-compose.yml`
   добавлена команда запуска с явными параметрами: `max_connections=25`
   (у приложения один пул на 10 соединений, сотня коннектов из умолчаний
   нам не нужна и стоит памяти), уменьшенные `shared_buffers`,
   `work_mem`, `maintenance_work_mem`.
2. **Потолок кучи Node** — `NODE_OPTIONS=--max-old-space-size=384` для
   контейнера приложения: при утечке или всплеске процесс упрётся в свой
   лимит и перезапустится, а не утащит за собой базу.
3. **Лимиты памяти контейнеров** — `mem_limit` на оба сервиса, чтобы
   всплеск в одном не убивал другой.

Что нужно сделать руками на сервере:

4. **Swap 2 ГБ** — обязательно, иначе `docker compose build` рискует
   получить OOM на шаге `next build`. Один раз:
   ```bash
   fallocate -l 2G /swapfile && chmod 600 /swapfile
   mkswap /swapfile && swapon /swapfile
   echo '/swapfile none swap sw 0 0' >> /etc/fstab
   ```
5. **Собирать образ до пика нагрузки**, а не в час пик: сборка временно
   съедает больше, чем работа.

Если памяти всё равно не хватает — собирать образ не на боевом сервере, а
локально или в CI, и привозить готовый. Это следующий шаг, до него доходим
только если упрёмся.

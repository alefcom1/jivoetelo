# Живое Тело — план реализации

> Обновлено: июль 2026. Рабочий план разработки. Полная продуктовая
> спецификация — в [product-spec.md](./product-spec.md); этот документ
> определяет, **что и в каком порядке строим на самом деле**, с учётом малой
> команды. При противоречии приоритет у этого плана.

## Зафиксированные решения

1. **Платформа запуска:** веб-SaaS на `jivoetelo.ru`. Telegram (бот / Mini App)
   — после работающего веб-ядра, на том же бэкенде.
2. **Хостинг:** VPS (reg.ru), Docker Compose, reverse proxy с TLS.
   Данные хранятся в РФ — это же закрывает требование локализации 152-ФЗ.
3. **База продуктов:** гибрид. LLM-оценки с диапазонами и пометкой
   «приблизительно» для обычных блюд; проверенные данные (штрихкоды — Open
   Food Facts, классические таблицы состава) для брендов; собственная
   верифицированная таблица растёт постепенно из пользовательских правок.
   Полноценную модерируемую базу из спеки (раздел 13.1) не строим заранее.
4. **Команда малая**, поэтому скоуп режется агрессивно (см. ниже).

## Отличия от спецификации (что сознательно отложено)

| Спека | Решение плана |
|---|---|
| Монорепо, NestJS, Redis, BullMQ, S3 (раздел 12) | Один Next.js-монолит + PostgreSQL + диск VPS. Разделяем на сервисы, только когда упрёмся. |
| Фаза 1: 7+ маркетинговых страниц, Storybook | Только текущий лендинг + рабочий лист ожидания. Интерактивное демо AI-камеры — позже, как отдельная задача. |
| Админ-панель (раздел 18) | Консоль БД / psql. Админку строим при реальной нагрузке на модерацию. |
| Pro для специалистов (фаза 4) | После появления удерживающихся пользователей. |
| Family, Pantry, планировщик, white-label | Вне горизонта планирования. |
| Telegram Mini App (фаза 5) | Сначала простой бот на том же API, Mini App позже. |

Что из спеки **сохраняем как обязательное**: языковые правила и правила
безопасности (разделы 4.2–4.3), три уровня уверенности AI и уточняющие
вопросы (15.2–15.3), абстракция AI-провайдера (15.1), структурированный
вывод модели, диапазоны вместо ложной точности (14.1), режим «скрыть
калории».

## Архитектура

- **Приложение:** Next.js (App Router, `output: "standalone"`), TypeScript
  strict. Серверные действия / route handlers вместо отдельного API-сервиса.
- **БД:** PostgreSQL 17 + Drizzle ORM (миграции в `drizzle/`).
- **Файлы (фото еды):** диск VPS за тонкой абстракцией хранилища, чтобы позже
  переехать на S3-совместимое без переписывания кода.
- **AI:** интерфейсы `MealVisionProvider` / `NutritionAssistantProvider`
  (раздел 15.1 спеки) с первого дня; конкретный провайдер — деталь реализации
  за интерфейсом. Значения КБЖУ считает наш код, модель возвращает состав и
  диапазоны порций.
- **Очереди/фоновые задачи:** пока нет; AI-разбор — в рамках запроса с
  честным статусом обработки. Очередь появится вместе с реальной нагрузкой.
- **Деплой:** Docker Compose (`app` + `db`), reverse proxy на VPS —
  см. [deploy-vps.md](./deploy-vps.md).

## Майлстоуны

### M0 — фундамент (эта ветка) ✅

- Уход со стартера OpenAI Sites (vinext/Cloudflare) на самостоятельный Next.js.
- Рабочий лист ожидания: PostgreSQL + Drizzle, server action, валидация,
  защита от дублей.
- Docker-сборка и compose для VPS, документация деплоя.
- Этот план.

### M1 — лендинг в бою

- Деплой на VPS, домен, TLS, бэкапы Postgres (cron + pg_dump).
- Self-hosted аналитика посещений (Plausible/Umami) — без передачи данных
  третьим сторонам.
- Купить `zhivoetelo.ru` (стандартная транслитерация) с редиректом.
- Сжать `og.png` (сейчас 2,2 МБ) до ~200 КБ.

### M2 — ядро продукта: дневник с AI-разбором

Одна вертикаль, без онбординга и целей:

- Аутентификация: e-mail + пароль или magic link (без SIWC, без соцсетей).
- Добавление приёма пищи текстом и фото → структурированный разбор
  (JSON-схема из раздела 15.2) → редактируемый черновик с уровнями
  уверенности и 1–2 уточнениями → сохранение.
- Лента дня и итоги (энергия, белок, клетчатка).
- Хранение фото с настройкой удаления.

**DoD:** новый пользователь регистрируется, логирует еду фото и текстом,
правит черновик, видит итоги дня. Языковые правила 4.3 соблюдены во всех
текстах интерфейса.

### M3 — цели и «что съесть дальше» v1

- Мини-онбординг (цель, профиль, активность, видимость калорий).
- Стартовые цели диапазоном (Миффлин-Сан Жеор, раздел 14.1).
- Вес + сглаженный тренд (EMA, раздел 14.3).
- Первая версия рекомендации «что съесть дальше»: детерминированные
  ограничения (остаток дня, исключения) + генеративное объяснение (15.5).

### M4 — удержание

- Недельный обзор (8.12, редакционный формат).
- PWA-обвязка, e-mail-напоминания (без чувства вины, раздел 19).
- Адаптивная корректировка целей с подтверждением пользователя (14.2).

### M5 — монетизация

- Тарифы Free / Premium (лимит AI-разборов на Free).
- ЮKassa: вебхуки, идемпотентность, льготный период.
- Оферта, согласия, экспорт и удаление данных (обязательны до приёма денег).

### M6 — Telegram

- Бот на существующем API: фото/текст/голос → разбор → подтверждение,
  итоги дня, напоминания. Привязка к веб-аккаунту с серверной проверкой
  подписи Telegram.

## Юридический чеклист (к юристу до M5)

- 152-ФЗ: регистрация оператора ПДн, политика, согласия; данные о питании и
  весе трактовать как чувствительные.
- Граница «не медицинское изделие» (раздел 4.1 спеки) — формулировки в
  интерфейсе и оферте.
- Проверка товарного знака «Живое Тело» (раздел 2.4).
- Оферта и правила подписки для ЮKassa.

## Главные риски

1. **Качество AI-разбора русских блюд** — валидировать на M2 на реальных
   тарелках, до инвестиций в M3+.
2. **Стоимость AI на пользователя** — считать юнит-экономику с первых
   пользователей; лимиты Free-тарифа проектировать от неё.
3. **Доступность внешних AI API с VPS в РФ** — абстракция провайдера +
   возможность проксировать вызовы; проверить на M2 первым делом.
4. **Один человек — узкое место** — не открывать новый майлстоун, пока не
   закрыт DoD предыдущего.

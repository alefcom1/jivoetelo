# Автодеплой через GitHub Actions

> Пошаговая инструкция. Настраивается один раз, дальше выкатка происходит
> кнопкой в интерфейсе GitHub или автоматически при пуше в `main`.

## Как это устроено

Workflow крутится **на серверах GitHub**, а не на вашей машине и не в среде
ассистента. Он забирает код, прогоняет проверки, подключается к вашему VPS
по SSH и выполняет там [`deploy/remote-deploy.sh`](../deploy/remote-deploy.sh):
обновляет код до точного коммита, пересобирает контейнеры, применяет
миграции и ждёт, пока приложение ответит на `/api/health`.

Если приложение не поднялось за две минуты — выкатка помечается неуспешной,
в лог печатаются последние строки логов контейнера и команда для отката.

```
push / кнопка → GitHub Actions → SSH → сервер: git reset → docker compose → миграции → health → IndexNow
```

Ассистент в этой цепочке не участвует: из его среды исходящий SSH закрыт.

**Последний шаг — уведомление поисковиков.** До выкатки сохраняется снимок
карты сайта, после — берётся новая, и разница уходит в IndexNow
(`scripts/indexnow.mjs`, устройство — в `lib/indexnow.ts`). Секретов шаг не
требует: ключ протокола публичный по замыслу и лежит в репозитории вместе с
файлом-подтверждением в `public/`. Оба шага помечены `continue-on-error` —
сорвавшееся уведомление не должно объявлять успешную выкатку неудачной.

## Шаг 1. Подготовить сервер (делается один раз)

Подключитесь к VPS по SSH и выполните по порядку.

### 1.1. Docker

```bash
curl -fsSL https://get.docker.com | sh
docker --version && docker compose version
```

### 1.2. Swap

Обязательно: пик сборки съедает больше гигабайта, и без swap она упадёт с
ошибкой нехватки памяти.

```bash
fallocate -l 2G /swapfile && chmod 600 /swapfile
mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
free -m
```

### 1.3. Код

Репозиторий публичный, ключи для чтения не нужны.

```bash
git clone https://github.com/alefcom1/jivoetelo.git /root/jivoetelo
cd /root/jivoetelo
```

### 1.4. Файл `.env`

Он намеренно вне git и переживает все выкатки — заполняется один раз.

```bash
cp .env.example .env
openssl rand -hex 24     # это значение → POSTGRES_PASSWORD
nano .env
```

Заполните как минимум:

| Переменная | Значение |
|---|---|
| `POSTGRES_PASSWORD` | сгенерированная строка |
| `DATABASE_URL` | `postgresql://jivoetelo:<пароль>@localhost:5432/jivoetelo` |
| `ANTHROPIC_BASE_URL` | `https://proxy.techperevod.com/api` |
| `ANTHROPIC_AUTH_TOKEN` | `PROXY_SECRET` воркера на Hetzner |
| `TELEGRAM_BOT_TOKEN` | токен от @BotFather, если запускаете Mini App |
| `LEGAL_*` | реквизиты оператора, когда появится ИП или ООО |

Проверьте, что ничего не забыто:

```bash
node scripts/preflight.mjs
```

Если Node на сервере нет — не страшно, проверка необязательная. Поставить:
`curl -fsSL https://deb.nodesource.com/setup_22.x | bash - && apt-get install -y nodejs`

### 1.5. Первый запуск вручную

**Важно: первый раз выкатите руками, не автодеплоем.** Так вы увидите
ошибки настройки сразу, а не через непонятный красный крестик в GitHub.

```bash
cd /root/jivoetelo
docker compose up -d --build     # первая сборка идёт несколько минут
./deploy/migrate.sh
curl -s "http://127.0.0.1:$(sed -n 's/^APP_HOST_PORT=//p' .env | tail -n1)/api/health"
```

Ожидаемый ответ: `{"status":"ok"}`.

### 1.6. Домен и TLS

```bash
apt-get install -y caddy
cp deploy/Caddyfile /etc/caddy/Caddyfile
nano /etc/caddy/Caddyfile        # поправить email для Let's Encrypt
caddy validate --config /etc/caddy/Caddyfile
systemctl reload caddy
```

A-запись `jivoetelo.ru` должна указывать на IP сервера **до** этого шага,
иначе Caddy не выпустит сертификат.

## Шаг 2. Ключ для деплоя

Отдельная пара ключей только для выкатки — не ваш личный ключ. Если она
утечёт, вы отзываете её одной строкой, не трогая свой доступ.

На сервере:

```bash
ssh-keygen -t ed25519 -f /tmp/deploy_key -N "" -C "github-actions-deploy"
cat /tmp/deploy_key.pub >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

Теперь покажите приватный ключ — его целиком, вместе со строками
`BEGIN`/`END`, нужно будет вставить в секрет GitHub:

```bash
cat /tmp/deploy_key
```

Скопируйте вывод, а затем **сразу удалите приватный ключ с сервера** — там
он больше не нужен и только создаёт риск:

```bash
rm /tmp/deploy_key
```

Публичный (`/tmp/deploy_key.pub`) уже записан в `authorized_keys`, его тоже
можно удалить.

### Отпечаток сервера

Нужен, чтобы выкатка шла именно на ваш сервер, а не на чужой, подставленный
в момент подключения. На сервере:

```bash
ssh-keyscan -t ed25519 localhost 2>/dev/null | sed "s/^localhost/$(curl -s ifconfig.me)/"
```

Команда выдаёт одну строку вида `123.45.67.89 ssh-ed25519 AAAA...` — она и
пойдёт в секрет. Сверьте, что отпечаток совпадает с настоящим ключом сервера:

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

## Шаг 3. Секреты в GitHub

Откройте `Settings` → `Secrets and variables` → `Actions` → `New repository
secret` и заведите четыре секрета:

| Имя секрета | Что положить |
|---|---|
| `DEPLOY_SSH_KEY` | приватный ключ целиком, из шага 2 (со строками BEGIN/END) |
| `DEPLOY_KNOWN_HOSTS` | строка с отпечатком сервера из шага 2 |
| `DEPLOY_HOST` | IP-адрес или домен сервера |
| `DEPLOY_USER` | пользователь SSH, обычно `root` |

Пятый — необязательный: `DEPLOY_PATH`, если код лежит не в
`/root/jivoetelo`.

Значения секретов не видны никому после сохранения, включая вас, и
маскируются в логах. Если ошиблись — просто перезапишите.

## Шаг 4. Первая выкатка

1. Откройте вкладку **Actions** в репозитории.
2. Слева выберите workflow **«Деплой на VPS»**.
3. Нажмите **Run workflow**, в выпадающем списке выберите ветку
   `claude/project-concept-review-3382m5` (пока работа идёт в ней) и
   подтвердите.
4. Откройте запустившийся прогон и следите за шагами.

Что происходит по шагам:

| Шаг | Что делает | Сколько идёт |
|---|---|---|
| Забрать код | Скачивает репозиторий на runner | секунды |
| Проверки | `npm ci`, линтер, тайпчек, 105 тестов | 1–2 минуты |
| Настроить SSH | Кладёт ключ и отпечаток | секунды |
| Выкатить | Всё, что на сервере | 2–5 минут |

Проверки идут **до** подключения к серверу: сломанный код до продакшена не
доезжает.

## Шаг 5. Дальше

- **Кнопкой** — вкладка Actions, «Run workflow», любая ветка.
- **Автоматически** — любой пуш в `main`. Пока вы работаете в отдельной
  ветке, автозапуска не будет; он включится сам, когда вы вольёте ветку в
  `main`.

Две выкатки одновременно не запустятся: вторая подождёт первую.

## Если что-то пошло не так

| Симптом в логе | Причина | Что делать |
|---|---|---|
| `Permission denied (publickey)` | Публичный ключ не попал в `authorized_keys` или не тот пользователь | Проверьте `cat ~/.ssh/authorized_keys` на сервере и секрет `DEPLOY_USER` |
| `Host key verification failed` | Секрет `DEPLOY_KNOWN_HOSTS` пустой или от другого сервера | Пересоздайте по шагу 2. Если меняли сервер — отпечаток другой |
| `Нет файла .env` | Не выполнен шаг 1.4 | Создайте `.env` на сервере вручную |
| `Проверка окружения нашла проблемы` | `preflight` нашёл пустой токен или словарный пароль | Прочитайте строки `FAIL` в логе, поправьте `.env` |
| `Приложение не ответило за две минуты` | Приложение не поднялось | В логе есть последние 60 строк контейнера — почти всегда там видно причину |
| Сборка падает без внятной ошибки | Кончилась память | Проверьте `free -m`: скорее всего нет swap (шаг 1.2) |

**Откат.** В конце неуспешной выкатки печатается готовая команда с хешем
предыдущей версии. Выполните её на сервере. Важно: миграции базы откатом не
отменяются — если упало после миграций, сначала разберитесь, что именно
сломалось.

## Если потерян доступ по SSH

`.env` лежит вне git и правится на сервере руками — пока туда пускают. Когда
не пускают, менять настройки становится нечем, хотя ключ выкатки продолжает
работать: GitHub Actions ходит на тот же сервер как ни в чём не бывало.

Для этого случая есть workflow **«Задать переменную в .env на сервере»**
(`set-env.yml`). Actions → выбрать его слева → Run workflow → выбрать имя
переменной из списка, вписать значение. Он допишет её в `.env`, сохранит
копию файла до правки, перезапустит контейнер и убедится, что тот видит новое
значение. Новых прав это не даёт: у того, кто может запускать workflow, и так
есть право отправить в `main` любой код и выкатить его.

Значение маскируется в логе, а в вывод идёт только длина: скрипт общий, и
однажды им зададут токен.

Список переменных намеренно закрытый — выпадающий список в `set-env.yml`,
новая добавляется одной строкой. Свободная строка здесь была бы худшим из
решений: опечатка в имени записывается без ошибки, приложение переменную не
читает, и выглядит это как «ничего не изменилось».

Три вещи, которые в этой ситуации выглядят как поломка, а ею не являются:

- **`Connection closed by <ip> port 22`** сразу после ввода пароля — это не
  «неверный пароль», а бан fail2ban. Каждая новая попытка продлевает срок
  (`docs/deploy-vps.md`, раздел 11).
- **Вставка нескольких команд разом.** `ssh` спрашивает пароль, а из буфера
  ему прилетают следующие строки — со стороны сервера это выглядит как
  подбор. Вводите по одной команде.
- **Не тот сервер.** `docker ps -a` показывает и остановленные контейнеры;
  если нужного среди них нет, вы не на той машине. Где какой compose-файл —
  спрашивать надо у самого Docker:
  `docker inspect $(docker ps -aq) --format '{{.Name}} → {{index .Config.Labels "com.docker.compose.project.working_dir"}}'`

## Безопасность

- Ключ отдельный и только для деплоя: компрометация не даёт доступа к вашим
  остальным серверам, отзывается удалением строки из `authorized_keys`.
- Отпечаток сервера зафиксирован заранее, а не принимается на доверии при
  подключении — иначе подмена сервера прошла бы незамеченной.
- Приватный ключ живёт только в секретах GitHub и на runner в момент
  выкатки; последним шагом workflow его удаляет.
- Секреты никогда не попадают в код и в логи.
- На сервере в git-отслеживаемых файлах не должно быть ручных правок:
  `git reset --hard` их сотрёт. Всё, что специфично для сервера, живёт в
  `.env` и в томах Docker.

**Возможное усиление на потом:** завести на сервере отдельного пользователя
в группе `docker` вместо `root`. Сейчас `root` выбран потому, что так уже
устроен соседний проект, и одинаковый порядок проще держать в голове.

## Что можно улучшить позже

Сейчас образ собирается **на самом VPS** — это просто, но требует swap и
занимает несколько минут на слабой машине. Когда захочется быстрее и
надёжнее: собирать образ в Actions (там памяти достаточно), публиковать его
в GitHub Container Registry, а на сервере только скачивать готовый. Тогда
`docker compose` на сервере перестанет собирать вообще, а выкатка станет
быстрой и предсказуемой. Это изменение затронет `docker-compose.yml`
(`image:` вместо `build:`) и добавит в workflow шаг публикации.
